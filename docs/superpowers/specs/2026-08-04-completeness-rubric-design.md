# sidedash — 상태 분석을 완성도 루브릭으로 단순화

## 배경 및 목적

기존 "상태 분석" 기능(`2026-08-02-project-status-analysis-design.md`)은 프로젝트가 최근
어디서 멈췄는지를 자유서술 문단으로 요약해 카드에 저장·표시했다. 이번 변경의 시작은
"완성도를 점수로, 다음 할 일을 한 줄로 보여주는 루브릭을 카드에 추가하면 어떨까"였는데,
논의 과정에서 다음 두 가지가 드러났다.

- 점수/다음 액션을 카드에 상시 노출하는 안(배지, 링 게이지 등)을 검토해보니, sidedash가
  원래 지향하던 "가벼운 메뉴바 런처"에 시각적 무게를 계속 얹는 방향이었다.
- 기존 프롬프트가 "완성도를 숫자로 매기지 말고, 계속할지 추천하지 말라"고 명시적으로 금지해둔
  이유도 동일하게 "카드에 너무 많은 내용이 쌓이는 것"을 막기 위해서였다.

결론은 **카드에는 아무것도 남기지 않는 것**이다. 완성도 점수와 다음 액션은 필요할 때 버튼을
눌러 로그 창에서 한 번 보고 흘려보내는 정보로 바꾼다. 이 방향이면 기존 프롬프트가 막아뒀던
이유(카드 과밀화)가 애초에 성립하지 않으므로, 점수화·다음 액션 제안을 다시 허용해도 된다.

결과적으로 이 작업은 새 기능 추가가 아니라, 기존 "상태 분석" 기능에서 **저장 계층과 카드
UI를 걷어내 로그 창 전용 1회성 액션으로 되돌리는 축소 작업**이다.

## 아키텍처

- **트리거·프로세스 실행 방식은 그대로 둔다.** 카드의 "🔍" 버튼 → 로그 창 오픈 →
  `claude -p` 헤드리스 실행 → stdout 스트리밍, 이 흐름과 기존 10분 타임아웃/프로세스 그룹
  종료 로직은 손대지 않는다.
- **결과를 어디에도 저장하지 않는다.** `analysis.json`(userData) 저장, `AnalysisResult` 타입,
  `ProjectCard.lastAnalysis` 필드를 모두 제거한다. 로그 창에 스트리밍된 텍스트가 유일한
  결과물이며, 창을 닫으면 사라진다.
- **카드 UI에서 분석 관련 요소를 모두 제거한다.** 요약 박스, "N일 전 분석"/"미분석" 태그,
  2줄 클램프·펼치기 로직을 삭제한다. 버튼만 남기고, 버튼 라벨은 "다시 분석" 토글 없이
  고정 문구("🔍 완성도 평가")로 바꾼다.
- **프롬프트를 점수+다음 액션 형식으로 교체한다.** 자유서술 요약 대신 아래 고정 2줄 포맷을
  요청한다. 카드에 저장/파싱하지 않으므로 엄격한 머신 파서블 포맷일 필요는 없지만, 로그
  창에서 한눈에 읽히도록 줄 형식은 고정한다.

  ```
  완성도: {0~100 사이 점수}%
  다음: {한 문장}
  ```

- **점수는 밴드 앵커를 준 루브릭 방식으로 매긴다.** "완성도 점수를 매겨줘"라고만 하면 매번
  다른 잣대로 채점해 프로젝트 간 점수를 신뢰하기 어렵다. 대신 점수 구간마다 "이 점수는 이런
  상태를 뜻한다"는 설명(앵커)을 프롬프트에 고정해두고, 그 설명에 맞춰 판단하게 한다 — 에세이
  채점이나 LLM-as-judge 평가에서 쓰는 표준적인 방식이다. 앵커는 모든 프로젝트에 공통으로
  적용되는 4단계뿐이고, "이 프로젝트의 핵심 플로우가 뭔지"는 프로젝트마다 미리 정의해두지
  않는다 — 매 실행마다 Claude가 README·소스 구조·git 로그를 읽고 그때그때 추론한다 (이미
  허용된 `Read`/`Glob`/`Bash(git log:*)` 도구로 충분하며, README 강제 요구 같은 별도 지시는
  추가하지 않는다).

  프롬프트 전문:

  > 이 프로젝트의 최근 git 커밋 로그와 소스 파일 구조를 읽고, 핵심 플로우가 어디까지
  > 동작하는지 판단해서 아래 기준으로 완성도 점수를 매기고 다음에 할 일을 제안해줘.
  >
  > 0~25: 뼈대만 있음 — 핵심 플로우가 끝까지 이어지지 않음
  > 26~50: 핵심 플로우 일부는 동작하지만 중간에 끊기거나 미구현된 지점이 있음
  > 51~75: 핵심 플로우는 처음부터 끝까지 동작하지만 에러 처리나 엣지케이스가 미흡함
  > 76~100: 핵심 플로우와 에러 처리까지 되어 있어 지금 상태로 계속 써도 무리 없음
  >
  > 프로젝트 전체가 뭘 하는 앱인지 설명하거나 예전 작업 히스토리를 정리하지 말고, 지금
  > 상태만 보고 판단할 것. 다음 할 일은 어떤 기능을 다뤄야 하는지 구체적으로 말하되 커밋
  > 해시나 파일 경로, 스크립트 이름 같은 지엽적인 디테일은 빼고 말할 것. 확인했다는 말이나
  > 서론 없이, 마크다운이나 글머리 기호 없이, 아래 두 줄 형식으로만 답할 것:
  >
  > 완성도: {점수}%
  > 다음: {한 문장}

- **완료 알림 라벨을 바꾼다.** `ANALYSIS_LABEL`을 "상태 분석" → "완성도 평가"로 바꿔
  macOS 알림 문구("완성도 평가 완료" 등)와 버튼 라벨을 일치시킨다.

## 데이터 흐름

1. 사용자가 카드의 "🔍 완성도 평가" 버튼 클릭.
2. 렌더러가 `window.api.runAnalysis(path)` 호출 → 메인 프로세스 `run-analysis` 핸들러.
3. 이미 실행 중이면 `already-running` 반환 (기존과 동일).
4. 로그 창 오픈 → `runAction()`에 `actionType: 'analyze'`로 위임 → `claude -p` 프로세스 스폰.
5. stdout/stderr가 로그 창으로 스트리밍 (`완성도: NN% / 다음: ...` 형식의 텍스트가 그대로
   찍힘).
6. 프로세스 종료 시: 저장 없이 `action-exited` 이벤트만 발생 → 렌더러가 프로젝트 목록을
   재조회하지만, `lastAnalysis` 필드 자체가 없으므로 카드에는 아무 변화가 없다.
7. 로그 창을 닫으면 결과는 사라진다. 다시 보려면 버튼을 다시 눌러 재실행해야 한다.

## 에러 처리

기존과 동일하게 새 에러 케이스를 만들지 않는다. `claude` CLI 실행 실패/비정상 종료는
`run.ts`의 기존 `child.on('error')` 및 종료 코드 처리를 그대로 따른다 (로그 창에 에러 출력,
실패 알림 표시). 저장 로직 자체가 없어지므로 "빈 요약이 기존 결과를 덮어쓰는" 이전의 예외
케이스(현재 `1546229` 커밋에서 다룬 것)도 함께 사라진다 — 애초에 발생할 수 없다.

## 테스트

- `analysis.ts`와 그 테스트(`analysis.test.ts`)를 삭제하므로 관련 Vitest 스펙도 함께
  제거한다.
- `run.test.ts`의 `buildAnalyzeCommand` 테스트는 기대값을 `ANALYSIS_PROMPT` 상수 자체로
  참조하고 있어 프롬프트 문구가 바뀌어도 별도 수정이 필요 없다 (실제로 확인함).
- `ipc/projects.test.ts`는 현재 `canAddProject`만 테스트하고 `getProjectCards`는 다루지
  않으므로, `analysisFilePath` 파라미터 제거에 따른 테스트 갱신 대상이 없다 (실제로 확인함).
- Electron UI는 기존 방침대로 자동화 테스트 대신 수동 검증 (버튼 클릭 → 로그 창에 점수/다음
  액션 형식으로 출력되는지, 카드에는 아무 것도 남지 않는지 확인).

## 스코프 밖

- 여러 프로젝트를 한 번에 평가하는 일괄 실행.
- 평가 결과를 어떤 형태로든 다시 저장하거나 이력 관리하는 기능.
- 점수 기반 정렬/필터링 (카드에 점수 자체가 남지 않으므로 대상이 아님).
- 프롬프트 출력 포맷의 엄격한 검증/파싱 (사람이 로그 창에서 읽는 용도이므로 파서를 만들지
  않는다).
